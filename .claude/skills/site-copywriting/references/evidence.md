# 調査根拠（site-copywriting スキル）

> 本書は SKILL.md の各規則の根拠（解決する問題・市場観察・品質根拠）の正本。規則の適否を議論するとき・規則を変更するときに読む。
> 品質6軸の定義は SKILL.md「ブランド固有原則」を参照。

## 調査概要

- **実施時期**: 2026-07（2026-07-17 実査）
- **方法**: 多段のエージェント調査
  - 4セグメント×複数クエリでサイト収集（検索上位偏重を避けるため比較記事・一覧経由も併用）
  - 共通コードブック（H1の型6分類・対比構文のカウント規則・抽象語密度の判定基準）に基づく構造化抽出。直接競合4社は二重抽出して突合
  - 3レンズ（見出しとレトリック／具体性と信頼／文体とCTA・FAQ）で規範候補化し、根拠・整合・品質の3視点で批評→修正反映（指摘21件すべて反映）
- **対象**: 24社を選定、本文を読めたのは23社（N=23）
  - a = 直接競合（情シス代行・伴走支援）: 8社
  - b = M365導入支援: 5社（SBテクノロジーは本文取得不可）
  - c = 生成AI導入支援: 6社
  - d = 参照品質枠（大手）: 4社
- **取得ページ種別**: トップページ＋サービス詳細ページ
- **数字の読み方**:
  - 出現率の主表記は「x/23社」＝サイト単位の採用率。ページ内の出現回数とは区別する（%は補助的にのみ使う）
  - セグメント間で傾向が割れる規範はセグメント別に記載する
  - 少数派パターン（例: 3/23社）を「業界標準」とは呼ばない
  - 原資料が「〜社程度」と幅を付けている数字は、本書でも「程度」を保持する
- **限界**（本書の数字を絶対視しないための注記）:
  - 小標本: セグメントあたり4〜8社
  - 供給側の観察のみ: 各サイトの受注実績・読者の反応は不明。「市場で多い」は「効果がある」を保証しない
  - 選定バイアス: 検索経由で収集したため、SEO投資済みサイトに偏る
  - 一時点の観測: 慣行は変化する。大規模な改稿の前には再実査を検討する
  - 集計の揺れ: 観点別レンズ間で数値が割れる項目があり、割れた場合は幅表記で書く（例: R-18）
  - 監査可能性: サイト別の構造化抽出（原集計データ）は調査セッション内にありリポジトリには保存していない。本書の数字はその要約であり、個別の数字を監査する必要が生じたら再実査する

## 規範化の判断構造

各規則は次の4要素を分離して判断した（頻出しているだけの慣行を規則に昇格させないため）:

- **市場慣行**: 何社が使っているか（x/23社）
- **品質評価**: 品質6軸（調査前に固定。調査結果から後付けしない）
- **nextb適合**: 小規模コンサル・準委任のみ・中立という実体との整合
- **リスク**: 誤認・誇張・陳腐化・保守負担

## 規則別の根拠

### R-01 事実にない情報を創作しない

- 解決する問題: 誇大・虚偽による信頼毀損。競合の型（数字近接・生声）を「形だけ」移植するときの創作の誘惑
- 市場観察: 対象外（調査から独立のブランド原則）
- 品質根拠: 軸4・軸5（裏づけと固有性は実在してこそ機能する）

### R-02 契約形態は準委任として誤読なく書く

- 解決する問題: 請負と誤解した引き合い・契約トラブル
- 市場観察: 対象外（自社の契約実態に基づく）。なお市場には「すべて対応可能」型の無限定宣言が5/23社程度あり、追随しない（R-16）
- 品質根拠: 軸1（誤読の防止）

### R-03 料金は確定済みの目安レンジで書く

- 解決する問題: 見積もりの誤認と請負への誤読
- 市場観察: 料金の具体額開示は10/23社（a=7/8・b=3/5・c=0/6・d=0/4）。開示自体は直接競合の事実上の標準で、目安レンジ規約は市場と整合している
- 品質根拠: 軸4（検証可能な数字）

### R-04 煽り・過大約束をしない

- 解決する問題: 誇大表現による信頼毀損。実務トーンからの逸脱
- 市場観察: 恐怖・緊急訴求は0/23社。敬体統一は23/23社。過大約束CTAも0/23社。感嘆符多用は同一運営の2/23社のみで、数字の物量が下支えする特殊解として参照外
- 品質根拠: 軸6・軸4（煽りでなく根拠で語る）

### R-05 見出しは名詞句を基本にし、数え上げ宣言文を使わない

- 解決する問題: 英語 "There are two..." 直訳調の不自然さ
- 市場観察: 定型名詞句は23/23社。数え上げ宣言文は0/23社（市場に存在しない）
- 品質根拠: 軸1・軸6

### R-06 不自然な読点を新規コピーで使わない

- 解決する問題: 決め技風の読点の乱用による広告調と、音読時の不自然さ
- 市場観察: 1件以上の使用は9/23社だが、うち7社は1件どまり。見出し級で常用するのは1/23社のみ（成立はしているが少数派戦略であり、業界標準ではない）
- 品質根拠: 軸6（口頭で切らない位置の読点は営業担当の発話として不自然）

### R-07 ヒーローに「誰向けか」と検証可能な数値を1つずつ置く

- 解決する問題: 誰向けか分からないヒーローと、根拠のない第一印象
- 市場観察: 直接競合6/8社が実施。c/d群はほぼゼロで、読者特定をしない大手型とは明確に分かれる
- 品質根拠: 軸2・軸4。小規模コンサルとして直接競合側の型を採るのは調査の示唆に基づく判断であり、観測事実ではない

### R-08 抽象語には具体を隣接させる

- 解決する問題: 社名を差し替えても成立する汎用文
- 市場観察: 抽象語→具体の隣接が明確なのは7/23社程度。抽象語が浮いていると指摘されたのは8/23社程度
- 品質根拠: 軸3・軸4・軸5

### R-09 主張の直後に裏づけを1つ置く

- 解決する問題: 主張と根拠が離れて主張だけが浮く状態。規模数字で戦えない小規模コンサルの信頼調達
- 市場観察: 数字を信頼装置に使うのは16/23社。ただし顧客成果の定量まで書くのは3/23社にとどまり、書ければ市場の空白を突ける
- 品質根拠: 軸4

### R-10 読者は状況の描写で特定する

- 解決する問題: 読者が「自分の話だ」と思えない抽象的な呼びかけ
- 市場観察: 状況・属性レベルの読者明示は12/23社（a=8/8・b=2/5・c=2/6・d=0/4）。直接競合では全社標準
- 品質根拠: 軸2

### R-11 お悩みは業務名と場面の粒度で書く

- 解決する問題: 「退職・属人化」の定番シナリオは直接競合7/8社が採用済みで、定番だけでは競合と見分けがつかない
- 市場観察: 業務タスク粒度まで下りるのは5/23社程度
- 品質根拠: 軸1・軸2・軸5

### R-12 導入後の変化を顧客主語の動詞で1文書く

- 解決する問題: 提供物の列挙で終わり、読者が導入後を想像できない
- 市場観察: 21/23社で変化の記述が弱いと判定された市場全体の穴。書けば少数側に立てる
- 品質根拠: 軸3・軸1

### R-13 事例は課題→介入→結果の三段で書く

- 解決する問題: 結果だけの事例は主張の言い換えにしかならず、証拠として機能しない
- 市場観察: 事例保有は15/23社だが、三段の接続が明確なのは4/23社程度。定量結果まで書くのは3/23社
- 品質根拠: 軸4・軸5

### R-14 顧客の一人称の生声を最低1箇所置く

- 解決する問題: 現状診断（2026-07-16）の「口語テクスチャ皆無」。編集調の地の文では書けない情報の欠落
- 市場観察: 生声引用は5/23社で全て直接競合セグメント（a=5/8。b・c・d群は0社。レンズ間で帰属が割れる1社はサイト別ダイジェストのセグメント区分に従いaに算入）。a市場で戦う上では差別化ではなく装備の欠落に近い
- 品質根拠: 軸5・軸6

### R-15 FAQは実際に聞かれた質問で構成する

- 解決する問題: 読者の懸念に答えないFAQは問い合わせの心理障壁を下げない
- 市場観察: 実務型FAQ保有は11/23社（a=7/8）。FAQを持つ11社のうち、解約・最低契約期間への明答は2〜3社、既存ベンダーとの役割分担への言及は0社
- 品質根拠: 軸2・軸4

### R-16 承っていないこと・顧客側に残る作業を明文化する

- 解決する問題: 無限定の約束は準委任の実態と乖離し、ミスマッチな引き合いを生む
- 市場観察: やらないことを正面から書くのは0/23社（最接近は制約事項を専用セクションで開示する1社）。量的上限・超過条件の明示は6/23社程度。調査では明示する側が信頼に接続すると評価された
- 品質根拠: 軸5（決めないと書けない固有情報）

### R-17 料金は条件とセットで、事例・FAQより前に一度提示する

- 解決する問題: 金額単独では読者が見積もりを立てられず、比較検討から外れる
- 市場観察: 料金開示10/23社は金額単独でなく時間・台数・期間等の条件とセットで提示。料金を中盤に置く早期開示は直接競合5/8社
- 品質根拠: 軸4・軸1（見積もりが立つ書き方）

### R-18 同一文末の3連続を書き直しのサインにする

- 解決する問題: 現状診断の「全文が同一の編集調」。ただし反復側が市場多数派である点に注意し、過剰な変化づけで実直な敬体基調から浮かせない
- 市場観察: 文末の単調・反復の指摘は8〜11/23社（レンズにより判定幅あり）。口語・話し言葉の意図的な差し込みは5/23社で中小向けセグメントに集中
- 品質根拠: 軸6

### R-19 CTAはクリック後に起きることを1要素予告する

- 解決する問題: 無色のCTA（「お問い合わせ」のみ）はクリックの心理コストを下げない
- 市場観察: 相談＋資料の2系統併置は15/23社（a=8/8）。「無料」明記は8〜9/23社で直接競合に集中。負担・心理コストの予告まで踏み込むのは6/23社
- 品質根拠: 軸3・軸1（負担予告は資料導線がなくても満たせる）

### R-20 ページ間で同一段落を使い回さない

- 解決する問題: 現状診断で home と about に同一段落の重複を確認。型で量産した印象とページ固有の情報密度の低下
- 市場観察: 対象外（現状診断由来）
- 品質根拠: 軸5

### R-21 H1は「対象読者・提供範囲＋サービス名」の名詞句を既定にする

- 解決する問題: スローガンH1は何のページか一読で分からない
- 市場観察: 名詞句H1は18/23社（a=8/8・b=5/5・c=4/6・d=1/4）。スローガン型H1は4/23社で大手コーポレートトップに集中し、知名度が担保する型のため参照外
- 品質根拠: 軸1・軸2

### R-22 対比構文は配置と量をページ単位で管理する

- 解決する問題: 現状診断の対比10箇所超。市場中央値1件・最大でも8件に対する明確な外れ値で、「型で量産した」印象の主因
- 市場観察: 使用は15/23社だが1サイトの中央値は1件。4件以上は4/23社。H1自体に対比・否定を置くのは2/23社。対比を使わないのは8/23社で、うちd群は4/4社すべてが対比ゼロ（実名の事実だけで語る型）
- 品質根拠: 軸5（同型の量産は固有性を殺ぐ）・軸1（対比は読者に2項の処理を強いる）
- 区分の補足: 総量管理は「意識的に外してよい既定値」ではなく超過にレビューで理由を求める水準のため、番号は選択帯（R-21〜R-26）のまま区分のみ推奨とした

### R-23 疑問形の呼びかけは課題セクション1箇所に限る

- 解決する問題: 疑問形の乱発による軽さと、見出しの型の不統一
- 市場観察: 採用は6/23社（a=4/8・b=2/5・c=0/6・d=0/4）で中小向けセグメント限定の慣行。採用社も課題セクション以外には広げていない
- 品質根拠: 軸2（課題の呼びかけが読者特定を担う）・軸1

### R-24 用語はページの主読者に合わせて二層で使い分ける

- 解決する問題: 経営層が読むページの専門用語過多と、担当者が読むページの冗長な解説
- 市場観察: 前提知識扱いが基調なのは13/23社。同一サイト内でページ別に出し分ける二層運用の明示は4/23社
- 品質根拠: 軸1・軸2

### R-25 英字eyebrowは装飾に徹する

- 解決する問題: 英字側に情報を持たせると読者に二重の読解を強いる
- 市場観察: 11〜12/23社が採用し、全セグメントで確認された装飾慣行。採用社は装飾に徹している
- 品質根拠: 慣行のみ（品質6軸に接続しない。装飾として許容）

### R-26 LPは課題起点ファネルの標準構成を維持する

- 解決する問題: 構成の場当たり的な組み替えによる検討動線の分断
- 市場観察: 直接競合はお悩みセクション保有7/8社・CTA終点のファネル構造8/8社で、既存標準構成は市場の王道と一致。カタログ型（概要→メニュー→料金）はM365導入系3/5社の型
- 品質根拠: 軸2（検討フェーズの疑問の順序に沿う）

### R-27 英語翻訳調を避け、日本のB2Bサイト慣用の言い回しに合わせる

- 解決する問題: 英語直訳調等の、日本の法人サイトとして不自然な言い回し
- 市場観察: 定型名詞句は23/23社（R-05に記載）。その他は個別規則の観察を参照
- 品質根拠: 軸6

## 運用課題

- **効果の観測**（導入後に見る指標）:
  - 問い合わせの質: 相談内容が想定読者・想定フェーズ（準委任前提・目安レンジ了解済み）と合っているか
  - CTA遷移: 相談・資料請求への遷移率の変化
  - 商談での言及: 「サイトのこの記述を見た」という言及の記録
- **顧客語彙コーパスの整備**（将来）:
  - 実際の相談・商談で聞かれた質問と言い回しを記録し、お悩み文（R-11）・FAQ（R-15）・声（R-14）の原資にする
  - 創作禁止（R-01）を守ったままテクスチャを増やす唯一の供給源
- **調査の賞味期限**:
  - 本書の市場観察は2026-07の一時点・23社の小標本。大規模な改稿の前には再実査を検討する
- **lintの運用**:
  - grepパターンは警告どまり（自動修正しない）を維持する。CIに組み込む場合も fail にせず警告表示にとどめる
