「Claude Code、来月から全社で使えるようにして」。経営会議でAI活用の号令が出て、情シスにこういう依頼が降ってくる。最近、この種の相談が増えました。

それで実際に環境を見せてもらうと、たいてい配布より先に別の問題が見つかります。社員が個人アカウントですでに使っている。APIキーの入ったフォルダをそのまま読ませている。そもそも誰が使っているのか、誰も把握していない。

Claude Code はファイルを読み、コマンドを実行するツールです。チャット型の生成AIとはリスクの質が違うので、「とりあえず配ってから考える」が通用しません。この記事では、導入支援の現場で毎回確認している「配る前の決め事」を8つにまとめました。想定読者は情シス担当者・CTO・管理部門の方です。

## 先にチェックリスト

1. 契約プランとデータの扱いを確認したか
2. アカウントの入口（SSO・個人アカウント）を決めたか
3. 入れてよいデータの線引きをしたか
4. 設定を「お願い」ではなく「強制」にできる形にしたか
5. 配布方法（手動 / MDM）を決めたか
6. ログ・証跡をどう残すか決めたか
7. ルール文書と例外承認の流れを作ったか
8. 定着の担当者と教育の場を決めたか

最初から8つ全部を完璧にする必要はありません。ただ、「どれを後回しにしたか」を自覚して配るのと、知らずに配るのとでは、事故が起きたときの立て直しがまったく違います。

## 1. 契約プランとデータの扱い

地味ですが契約からです。ここを個人向けプランの延長で進めてしまうと、あとで全部やり直しになります。

法人利用なら Team か Enterprise。選ぶ基準は人数ではなく統制要件です。SCIMによるアカウントの自動連携、監査ログ、コンプライアンス系の管理機能が要る——そうなった時点で Enterprise が視野に入ります（SSO自体は Team でも使えます。どの機能がどちらのプランかは契約時に最新の提供条件を確認してください）。迷うなら Team で小さく始めて、要件が固まってから引き上げる。私が支援している案件でも、この順番を取ることが多いです。

「入力したデータが学習に使われるのか」は稟議で最初に聞かれる質問ですが、法人プラン・API経由の利用では学習に使われない扱いが基本です。ただしここは「基本」としか書きません。契約時点の規約と管理画面の設定を、必ず自分の目で確認してください。確認した画面のスクリーンショットを残しておくと、後々の説明が楽になります。

なお Amazon Bedrock など主要クラウド経由の提供もあるので、すでにAWS等の統制基盤がある会社ならその中で完結させる手もあります。このあたりの提供形態は変化が速いので、契約時に最新情報を見てください。

## 2. アカウントの入口（SSO・個人アカウント）

配布の設計より先に、いま誰が使っているかを調べることをおすすめします。会社が正式に配る前から個人アカウントで使っている社員は、体感ではかなりの確率でいます。利用実態の調査を手伝うと、管理側の想定より多くの利用者が見つかるのが常です。

やることは3つだけです。会社ドメインのアカウントへの集約（個人アカウントでの業務利用をルールで禁止する）、SSOが使えるプランなら Entra ID などのIdP経由に認証経路を一本化すること、そして退職・異動時にアカウントが確実に止まる導線の確認。3つ目は忘れられがちですが、退職者のアカウントが生きている状態は、監査でいちばん説明に困ります。

ちなみに、先に調べた「個人アカウント利用の実態」は、経営に統制の必要性を説明する材料としてそのまま使えます。

## 3. 入れてよいデータの線引き

Claude Code はローカルのファイルを読みます。端末に置いてあるものは何でも入力になり得る、という前提で考えてください。

ここで規程を分厚くしても読まれません。現場が3秒で判断できる一覧で十分です。たとえば——

- 絶対ダメ: 顧客の個人情報、取引先から預かったデータ、APIキーやパスワード
- 条件付きOK: 社内のコードや文書（法人プラン契約の範囲で）
- 迷ったら: ◯◯さんに聞く

最後の「迷ったら」の行き先を書いておくことが、実は一番効きます。ここが後述の例外承認フローにつながります。

## 4. 設定の「強制」— managed settings

ガイドラインは善意で守られるもの、設定は強制されるものです。この区別が統制設計の肝です。

Claude Code には管理者側で設定を強制する仕組み（managed settings）があり、ユーザーやプロジェクトの設定では上書きできません。会社として禁止したい操作や接続先は、ルールに書くだけでなくここで縛ります。中身は3で決めた線引きからの逆算で、認証情報ファイルへのアクセス禁止や外部接続先の限定あたりが定番です。

「便利に使ってもらうための推奨設定の配布」と「事故らせないための強制設定」は役割が違うので、分けて設計してください。前者だけ配って統制した気になっているケースを時々見かけますが、それはガイドライン導入と同じで、各自の善意頼みです。

## 5. 配布方法（手動 / MDM）

パイロットの数人なら手順書ベースの手動セットアップで足ります。全社に配るなら Intune や Jamf などのMDMに載せて、本体のインストールから、管理側で強制する設定ファイル（managed settings）の配置までをセットで自動化します。

判断基準はシンプルで、「社員全員に手順書どおりの作業をしてもらって、全員が同じ状態になると信じられるか」。信じられないならMDMです。エンジニア以外の部門にも配る計画があるなら、なおさら「インストール後すぐ使える」状態で配る設計にしておかないと、問い合わせ対応で情シス側が回らなくなります。

## 6. ログ・証跡

導入して1〜2ヶ月すると、経営か監査から必ず「誰がどれくらい使っているのか」と聞かれます。そのときに管理画面を開いて答えられればよい、くらいのラインをまず決めてください。最初から立派なログ基盤を作る必要はありません。

具体的には、誰が・いつ・どのプロジェクトで・どんな操作（コマンド実行や外部接続）をしたか。ここまで説明できれば大半の場面はしのげます。監査要件が強い会社だけ、監査ログやテレメトリ（OpenTelemetry対応）でどこまで記録できるかを導入前に確認しておくとよいです。

ログを取っていることを利用者に伝えるのも忘れずに。それ自体が抑止になります。

## 7. ルール文書と例外承認

利用ガイドラインは、すでに生成AIの利用ルールがあるならその改訂で足ります。新しい文書を一から作るより、Claude Code 特有の論点——ファイルアクセス、コマンド実行、外部接続——を追記するほうが、書くのも読むのも早い。

それより大事なのが例外承認です。「原則禁止だが業務上必要」というケースは必ず出ます。例外の出口がないルールの末路は2つしかなくて、破られるか、業務が止まるか。申請と承認の流れは、Slackのワークフロー程度の軽いもので構わないので、最初から用意しておいてください。

## 8. 定着（教育と推進役)

初回の説明会でやるべきことは1つで、「何を入れてはいけないか」を機能紹介より先に伝えることです。

あとは社内の一次相談窓口を1人決めて、質問が情シスとベンダーに散らばらないようにする。月1回30分でもいいので、使い方やユースケースを共有する場を回す。パイロット段階なら、この程度でも十分回ります。

統制だけ固めて放置すると、そのうち使われなくなって、導入自体が失敗扱いになります。統制と定着は同時に設計したほうがうまくいく、というのがこれまで支援してきた中での実感です。

## ISMS運用中の会社への補足

ISMS（ISO/IEC 27001）を回している会社なら、話はむしろ早いです。新しい規格や文書体系は要りません。

リスクアセスメントに「生成AIツールの利用」を情報資産・リスクとして追加する。3で決めた線引きを既存の情報分類ルールと揃える。6のログを内部監査で見せられる形にしておく。既存のISMSの語彙に翻訳して載せるだけで、審査でも運用でも説明がしやすくなります。

## まとめ

8項目を挙げましたが、パイロット段階なら 1・2・3・7 だけで始められます。4・5・6・8 は全社展開までに固める。この2段階が現実的です。

自社の場合はどこから手を付けるべきか——を整理したい方は、[生成AI・Claude Codeの社内統制支援](/genai-governance/)のページをご覧ください。現状の利用状況と環境をお聞きして、優先順位を整理したうえでご提案しています。
