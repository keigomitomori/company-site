Claude Code の導入相談を受けるとき、最初にお伝えしていることがあります。**つまずくのは技術ではなく、「配る前の決め事」が足りないまま配ってしまうことです。**

Claude Code はターミナルで動くAIコーディングエージェントで、ファイルの読み書きやコマンド実行までこなします。便利さの裏返しとして、「誰が・どの端末で・どんなデータに触れるのか」を決めずに配ると、シャドーAI化や機密の持ち出しリスクに直結します。

この記事では、企業への導入・統制設計を支援してきた経験から、**配布前に決めるべき8項目**をチェックリスト形式でまとめます。対象読者は、Claude Code の導入を検討している情シス担当者・CTO・管理部門の方です。

## 先に結論: 配布前チェックリスト8項目

1. 契約プランとデータの扱いを確認したか
2. アカウントの入口（SSO・個人アカウントの扱い）を決めたか
3. 入れてよいデータ・ダメなデータの線引きをしたか
4. 設定を「お願い」ではなく「強制」できる形にしたか
5. 配布方法（手動 / MDM）を決めたか
6. ログ・証跡をどう残すか決めたか
7. ルール文書と例外承認の流れを作ったか
8. 定着の担当者と教育の場を決めたか

以下、それぞれ「なぜ必要か」「何を決めるか」を説明します。

## 1. 契約プランとデータの扱い

最初に決めるのは契約形態です。個人向けプランの延長で使わせるのではなく、法人プラン（Team / Enterprise）を前提にしてください。

- **学習利用の扱い** — 法人プラン・API経由の利用では、入力データがモデルの学習に使われない扱いが基本です。ただし契約時点の規約・設定を必ず自社で確認してください
- **Enterpriseを選ぶ目安** — SSOやSCIM、監査ログ、コンプライアンス系の管理機能が要件になるなら Enterprise が候補になります。人数だけでなく「統制要件」でプランを選ぶのがポイントです
- **APIやクラウド経由** — Amazon Bedrock など主要クラウド経由の提供もあり、既にAWS等の統制基盤がある会社ではその中で完結させる選択肢もあります（提供形態は変化が速いため契約時に最新情報を確認してください）

実務では「とりあえずTeamで開始し、SSO・監査要件が固まった段階でEnterpriseに引き上げる」という段階導入もよく取ります。

## 2. アカウントの入口（SSO・個人アカウント）

配布前に一番事故が起きやすいのがここです。**会社が配る前から、社員が個人アカウントで使い始めているケースは珍しくありません。**

- 会社ドメインのアカウントに集約し、個人アカウントでの業務利用をルールで明確に禁止する
- SSO（シングルサインオン）が使えるプランなら、IdP（Entra ID など）経由に寄せて認証経路を一本化する
- 退職・異動時にアカウントが確実に止まる導線（SCIMやオフボーディング手順）を確認する

「個人アカウントの利用実態がどれだけあるか」を先に調査すると、経営への説明にも使えます。

## 3. 入れてよいデータの線引き

Claude Code はローカルのファイルを読みます。つまり、**端末に置いてあるものは何でも入力になり得る**という前提で線引きが必要です。

- 顧客の個人情報・取引先から預かったデータ・認証情報（APIキーやパスワード）は入力禁止、のような「絶対NG」を短く定義する
- 「社外秘だが業務に必要」なデータは、条件付きで許可する範囲を決める（例: 法人プラン契約下のリポジトリ内コードは可、など）
- 判断に迷うケースの相談先を決めておく（後述の例外承認フローにつながります）

線引きは長い規程より、**現場が3秒で判断できる一覧表**にするのが定着のコツです。

## 4. 設定の「強制」— managed settings

ガイドラインを作っただけでは、設定は各自の善意に依存したままです。Claude Code には管理者側で設定を強制する仕組み（managed settings）があり、ユーザーやプロジェクトの設定より優先されます。

- 会社として禁止したい操作・接続先を managed settings 側で定義し、端末上で上書きできない形にする
- 「推奨設定テンプレートの配布」と「強制設定」を分けて考える。配布は利便性、強制は統制です
- 何を強制すべきかは、3で決めたデータの線引きから逆算します（例: 認証情報ファイルへのアクセス禁止、外部接続先の限定、テレメトリの有効化など）

ルールと設定強制のセットで初めて「統制」と呼べる状態になります。ここが「ガイドラインだけ導入」との最大の違いです。

## 5. 配布方法（手動 / MDM）

対象人数と端末管理の成熟度で決めます。

- **少人数・パイロット段階** — 手順書ベースの手動セットアップで十分です
- **全社展開** — Intune や Jamf などのMDMで、本体・設定ファイル・managed settings を配布する形に寄せると、バージョンや設定のばらつきを防げます
- 既にMDMでPCを管理している会社なら、Claude Code も「管理された配布物」に載せるのが自然です

エンジニア以外（コーポレート部門など）にも配る計画があるなら、なおさら「インストール後すぐ業務で使える」状態で配布する設計が効きます。

## 6. ログ・証跡

導入後に必ず聞かれるのが「誰が何に使っているのか」です。

- 法人プランの管理画面で確認できる利用状況を、月次で見る運用を決める
- 監査要件が強い場合は、監査ログやテレメトリ（OpenTelemetry対応）でどこまで記録できるかを事前に確認する
- 「ログを取っていること」を利用者に伝えることも、抑止として機能します
- 最低限、「誰が・いつ・どのプロジェクトで・どんな操作（コマンド実行や外部接続）をしたか」を説明できる状態を目指します

完璧なログ基盤を最初から作る必要はありません。**「これだけは説明できる」ラインを決めておく**ことが重要です。

## 7. ルール文書と例外承認

- 利用ガイドラインは、既存の生成AI利用ルールがあるならその改訂で対応し、Claude Code 特有の論点（ファイルアクセス・コマンド実行・外部接続）を追記する
- 「原則禁止だが業務上必要」なケースのために、例外申請と承認の流れを最初から用意しておく。例外の出口がないルールは、破られるか、業務を止めるかのどちらかになります

## 8. 定着（教育と推進役）

配って終わりにしないための最後のピースです。

- 初回の説明会で「何ができるか」より先に「何を入れてはいけないか」を伝える
- 社内の一次相談窓口（推進担当）を決め、質問がベンダーや情シスに散らばらないようにする
- 利用状況を見ながら、勉強会やユースケース共有の場を月次程度で回す

経験上、**統制と定着は同時に設計した方がうまくいきます**。締めるだけでは使われず、緩めるだけでは事故が起きやすくなります。

## ISMS運用中の会社への補足

ISMS（ISO/IEC 27001）を運用している場合、Claude Code の導入は次の形で既存の枠組みに載せられます。

- リスクアセスメントに「生成AIツールの利用」を情報資産・リスクとして追加する
- 3で決めたデータの線引きを、既存の情報分類ルールと整合させる
- 6のログ・証跡を、内部監査で説明できる形にしておく

新しい規格や特別な文書体系は必須ではありません。**既存のISMSの語彙に翻訳して載せる**のが、審査対応としても運用としても軽くなります。

## まとめ

8項目を並べましたが、すべてを完璧にしてから配る必要はありません。パイロット段階なら 1・2・3・7 だけでも始められます。全社展開の前に 4・5・6・8 を固める、という2段階が現実的です。

「自社の場合はどこから手を付けるべきか」を整理したい方は、[生成AI・Claude Codeの社内統制支援](/genai-governance/) のページをご覧ください。現状の利用状況・環境をお聞きして、優先順位を整理したうえでご提案しています。
